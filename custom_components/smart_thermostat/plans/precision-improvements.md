(детская, гостиная, спальня).

## P0 — дефекты, из-за которых точность деградирует прямо сейчас

### P0-1. Все предиктивные механизмы мягкой посадки — мёртвый код

Три блока в [`_handle_active_control()`](../controller.py:1091) должны гасить коррекцию
у цели, но их условия недостижимы: `_handle_active_control` вызывается только при
`|e| > deadband`, а пороги срабатывания при реальных heating_rate НИЖЕ deadband:

| Механизм | Условие | Порог (гостиная) | Порог (спальня) | deadband |
|---|---|---|---|---|
| overshoot-фактор ([1209](../controller.py:1209)) | `e/heating_rate < predict_minutes` | e < 0.293 | e < 0.132 | 0.3 / 0.5 |
| TTT-фактор ([1202](../controller.py:1202)) | `e*mpd < ttt_soft_min` | e < 0.161 | e < 0.046 | 0.3 / 0.5 |
| финальная отсечка ([1218](../controller.py:1218)) | `e/heating_rate < ttt_soft_min` | e < 0.146 | e < 0.066 | 0.3 / 0.5 |

Подтверждено расчётом по фактическим heating_rate/mpd из storage. У детской работает
только TTT-фактор (e < 2.5), остальные тоже мертвы. Итог: у цели система входит в
мёртвую зону с полной коррекцией PID (+1.0) → TRV догревает «по инерции» → overshoot
(overshoot_count 19/19 это подтверждает), затем hold медленно спускает уставку.

**Исправление:** заменить время-зависимые пороги на ошибку-зависимый easing,
привязанный к deadband, например:
```python
# Мягкая посадка: в зоне (deadband, deadband + ease_span) гасим коррекцию к 0
ease_span = max(1.0, 2.0 * deadband)
if e < deadband + ease_span:
    correction *= clamp(e / (deadband + ease_span), 0.2, 1.0)
```
Финальную отсечку уставки тоже перевести на этот же диапазон (плавно к baseline),
а не на `predicted_time < ttt_soft_min`.

### P0-2. I-член PID масштабирован по секундам — насыщение за один тик

[`PIDController.update()`](../pid.py:50): `self.i += self.ki * e * dt`, где `dt` в
СЕКУНДАХ. При interval=240 с и e=0.6: прирост интеграла = 0.05·0.6·240 = 7.2 → кламп
к `i_limit=1.0` за ОДИН тик. I-член работает как реле: любая ошибка дольше одного
тика мгновенно даёт максимальную коррекцию +1.0 и держит её до входа в мёртвую зону.
PID фактически вырожден в P + bang-bang. Это прямой источник overshoot.

**Исправление:** нормализовать dt к минутам: `self.i += self.ki * e * dt / 60.0`.
Тогда прирост = 0.05·0.6·4 = 0.12/тик → интеграл растёт постепенно и реально
участвует в регулировании. `i_limit = step_max` оставить (инвариант).

### P0-3. valve_exercise хранится в монотонных часах — сбрасывается рестартом HA

[`get_valve_exercise()`](../storage.py:395) пишет `hass.loop.time()` (монотонные
часы, обнуляются при каждом рестарте HA), а сравнение в
[`_tick()`](../controller.py:1375) — `now_mono - last_ex >= days*86400`. После
рестарта HA `now_mono` ≈ 0 < last_ex → разница отрицательная → автопрокрутка
откладывается на новые 7 дней аптайма. При рестартах чаще раза в неделю клапан
НИКОГДА не прокручивается → залипание.

**Исправление:** хранить epoch (`time.time()`); при чтении значения < 1e9 (старый
монотонный формат) считать «никогда» → одна автопрокрутка после обновления,
дальше — корректно.

## P1 — качество обучения и диагностики

### P1-1. Таймстампы историй: монотонные часы vs epoch

Истории offset/heating_rate/overshoot пишутся с `hass.loop.time()`
([storage.py:204](../storage.py:204), [246](../storage.py:246), [305](../storage.py:305)),
а `_cleanup_entry_history()` сравнивает с `time.time() - 7 дней` (epoch). Любой вызов
`cleanup_old_data()` удалит ВСЮ историю (монотонные ~1e6 всегда «старше» cutoff).
Сейчас метод никем не вызывается — бомба замедленного действия. Исправление: писать
epoch везде (см. P0-3).

### P1-2. ACTION_MAPPING отстал от фактических last_action

[`ACTION_MAPPING`](../sensor.py:49) не знает ~10 реальных действий:
`skipped_no_change`, `anti_chatter`, `hvac_off_valve_closed`, `valve_exercise`,
`operational`, `waiting_sensors`, `init_error_retry`, `set_hvac_mode_failed`,
`deadband_step_down` → сенсор `last_action_text` показывает «unknown», диагностика
слепая именно в интересных местах (анти-спам, посадка, прокрутка).

### P1-3. heating_rate EMA замусоривается отрицательными dT

[`_update_heating_rate()`](../controller.py:887) усредняет и падения температуры
(открыли окно/дверь) — в истории спальни есть значения −0.033. Отрицательный
heating_rate отключает всю предикцию (гард `> 0.001`). Исправление: при нагреве
(e > deadband) усреднять только dT > 0; отдельно оценивать **скорость остывания**
(полезна для прогноза overshoot после закрытия клапана).

### P1-4. Overshoot auto-tune не персистится

Снижение `_learn_rate_slow` при перегревах ([1136](../controller.py:1136)) живёт
только в runtime — после reload возвращается значение из опций. Записывать
результат в storage.

### P1-5. Мёртвые опции (обещано в UI, не используется в логике)

- `CONF_HUMIDITY_SENSOR` ([const.py:22](../const.py:22)) — нигде не читается.
  Идея: влажностная компенсация (ощущаемая температура) или хотя бы убрать из формы.
- `CONF_WEATHER_FORECAST_TYPE` — не читается; feedforward берёт `forecast[0]` из
  атрибута, которого в HA 2026 уже нет (forecast теперь через сервис
  `weather.get_forecast`). Погодная компенсация фактически работает только по
  текущей `temperature`.
- `CONF_MAX_STUCK_BIAS` и `_stuck_bias` — пишутся/сбрасываются, но ни на что
  не влияют (dead config). Либо реализовать, либо удалить из формы.

### P1-6. Change_count не персистится

Счётчик `change_count` обнуляется при каждом reload — критерий «здоровья» из правил
невозможно наблюдать на длинном окне. Писать в storage (раз в N изменений).

## P2 — фичи «магии точности»

### P2-1. Взвешенное усреднение датчиков
Гостиная = средняя(гостиная, кухня). Кухня систематически теплее → заниженная
средняя → перегрев гостиной. Добавить опцию весов или исключать датчик по
стат-отклонению от медианы.

### P2-2. Асимметричный deadband
Нагрев включать при e > +0.3, а «остывать отпускать» при e > −0.7 (перегрев терпим
дольше, зато нет дребезга уставки). Уменьшает total_changes и overshoot-chatter.

### P2-3. Stuck-underheat детект
Stuck detection ловит только перегрев ([_handle_stuck_detection](../controller.py:912)
работает при e < −deadband). Обратный случай — комната не греется при e > deadband
(клапан закрыт по switch, TRV не принял команду, местная калибровка врёт) —
не детектится. Добавить: при e > deadband и dT ≈ 0 за stuck_seconds — переотправить
уставку/открыть клапан + warning в лог.

### P2-4. Преднагрев под расписание
Автоматизация прыгает 18→23 °C в 18:00. При mpd=108 мин/°C выход на цель ≈ 9 часов.
Варианты: сдвинуть расписание автоматизации (быстро), либо фича интеграции
«достичь T к времени X» (prediction старта по mpd).

### P2-5. Гигиена кода
- `climate.py`/`config_flow.py`: локальные копии `_normalize_entity_list`/`_to_float`
  → перевести на `helpers.py`.
- `target_temperature_step` у виртуального термостата (UX).
- Orphan-записи в storage (`01KHC82HDR90E7Q92QQ8D8FWR0`, `01KHCEH2MJXVYBX9Y2J5XBD6F0`)
  — данные от удалённых записей, можно вычистить.

## Порядок внедрения

1. **P0-2 + P0-1** (в одном заходе: PID-масштаб + easing посадки) — устраняют главный
   источник overshoot. Наблюдать 2–3 дня по overshoot_count и графику.
2. **P0-3 + P1-1** (epoch в storage) — один заход, миграция тривиальная.
3. **P1-2** (ACTION_MAPPING) — быстрый, сразу виден эффект в диагностике.
4. Остальное по мере возможности; P2-1/P2-2 обсудить с пользователем (меняют
   поведение, которое он наблюдает).

## Критерии успеха

- overshoot_count не растёт (0 новых за неделю);
- комната входит в deadband без «горба» > 0.3 °C над целью;
- offset в ±3 °C, total_changes < ~50/день на запись;
- valve_exercise срабатывает раз в 7 дней по факту;
- `last_action_text` без «unknown».
